## Step 0. 개발 룰·API 규격 확정 (F-21)

- 할 일: 공통 룰 파일을 PR로 올려 세 명이 확인하고, 기능끼리 주고받는 데이터 형식을 문서 하나에 정리한다.
- 결과물: 공통 룰 PR 머지, 규격 문서 1개
- 확인: 세 명 모두 룰 PR을 승인하고 규격 문서에 4개 항목이 채워지면 완료

<details markdown="1">
<summary>기술 세부 내용</summary>

- 공통 룰 파일 6개는 [공통 룰](common-rules.md) 탭 참고. `.gitattributes`는 줄바꿈이 한꺼번에 바뀌므로 커밋을 따로 나눈다.
- 규격 문서 `docs/contracts.md`

| 규격 | 만드는 사람 | 쓰는 사람 |
|---|---|---|

</details>

## Step 1. 설치·실행 자동화 (F-22)

- 할 일: 교수님 가이드대로 새로 설치해 보고 막히는 곳을 고친 뒤, 설치와 실행을 스크립트 하나로 묶는다. AI 모델은 저장소에 이미 있는 작은 모델(Qwen3-1.7B)을 기본값으로 고정한다.
- 결과물: 설치 스크립트, 실행 스크립트 (Windows용·Mac용 각각)
- 확인: Windows와 Mac 양쪽에서 자동 테스트가 모두 통과하고, 챗봇·법규 질의응답이 답하면 완료

<summary>AI에게 붙여넣을 지시문</summary>

```
docs/guides/guide-ai-platform-oh.md의 Step 1을 읽어줘.
app/과 scripts/에서 read_text, write_text, open을 encoding 없이 쓰는 곳을 전부 찾아서 목록으로 보여줘.
고치기 전에 목록부터 확인할게.
```

</details>

<details markdown="1">
<summary>기술 세부 내용</summary>

- `docker/maria_db.yml` 포트를 `127.0.0.1:3379:3306`으로 고정 (같은 와이파이의 다른 사람 접근 차단)
- 파일 입출력에 `encoding="utf-8"` 누락 수정 (Windows 한글 깨짐)
- `scripts/setup.ps1`·`setup.sh`: 가상환경 → 패키지 → 데이터 스냅샷 확인
- `scripts/run.ps1`·`run.sh`: API 서버 + 화면 동시 실행

- `.env.example`의 `LOCAL_MODEL_NAME`을 `Qwen/Qwen3-1.7B`로 변경 (코드 기본값과 같음, 약 4GB). 모델 비교·속도 측정은 하지 않음

</details>

## Step 2. 최적화·챗봇 이력 DB (F-24)

- 할 일: 최적화를 돌린 결과와 챗봇 대화를 DB에 한 줄씩 저장한다. 나중에 이력 화면에서 다시 보거나, 틀린 답을 찾거나, 발표에서 사용 기록을 보여 줄 때 쓴다.
- 결과물: 저장 테이블 2개
- 확인: 최적화·챗봇을 한 번씩 쓰고 DB에 기록이 생기는지, DB를 꺼도 기능은 그대로 되는지 확인하면 완료

<summary>기술 세부 내용 (테이블 설명)</summary>

## Step 3. 배차 상담 챗봇 (F-25)

- 할 일: "160번 내일 3시 붐벼?", "버스 늘리려면 뭐 해야 돼?" 같은 질문을 받아 알맞은 기능(승객 예측, 배차 권고·최적화, 시뮬레이션, 법규 질의응답)을 골라 부르고 그 결과로 답한다. 어떤 기능을 부를지는 질문 속 단어로 정한다(작은 AI 모델에 고르게 하지 않음).
- 지킬 것: 숫자는 기능이 돌려준 값만 쓴다. 근거가 없으면 "찾을 수 없음"이라고 답한다.
- 결과물: 챗봇 기능(API) 1개, 자동 테스트 2개, 챗봇 채점 결과
- 확인: 김주혜의 챗봇 채점 문제집(F-33)에서 맞는 기능을 고른 비율이 90% 이상이면 완료
- 박성훈의 최적화·시뮬레이션이 끝나기 전에는 가짜 응답으로 먼저 만든다.

<details markdown="1">
<summary>AI에게 붙여넣을 지시문</summary>

```
docs/guides/guide-ai-platform-oh.md의 Step 3을 읽어줘.
app/core/rag.py가 질문을 받아 답하는 흐름을 먼저 설명해줘.
그다음 키워드 규칙으로 의도 분류 → 기능 호출 → Qwen3-1.7B로 답변 작성 구조의 app/core/agent.py 설계안을 알려줘.
```

</details>

<details markdown="1">
<summary>기술 세부 내용</summary>

- 흐름: 질문 → 의도 분류 → 값 뽑기(노선·날짜·시간) → 기능 호출 → 답변 작성 → 숫자 검증
- 파일: `app/core/agent.py`, `app/core/prompts.py` (기존 `rag.py`의 `SYSTEM_MESSAGE`도 여기로)
- 의도 분류: 키워드 규칙 (Qwen3-1.7B는 기능 선택을 맡기기엔 불안정). 상세: [기능별 설계](algorithms.md)의 F-25
- 요청·응답

```json
요청: {"message": "160번 10월 28일 오후 3시에 혼잡해?", "history": []}
응답: {"answer": "...", "tools": [{"name": "predict", "args": {}}],
       "sources": [{"doc": "...", "article": "..."}], "needs_review": true}
```

</details>

## Step 4. 법규 답변 정확도 개선 (F-26)

- 할 일: 작은 모델(Qwen3-1.7B)이 법규 질문에 더 많이 맞히게 고친다. 기존 채점에서 이 모델은 12문항 중 6개를 맞혔다. 지어낸 답은 없었지만, 근거 조항을 찾고도 "모른다"고 답한 문항이 있었다.
- 결과물: 고치기 전·후 채점 결과
- 확인: 김주혜의 40문항 문제집(F-32)에서 지어낸 답 0건을 지키면서 정답 수가 늘면 완료

<details markdown="1">
<summary>기술 세부 내용</summary>

- 기준선: README 평가표 2단계(1.7B, 조항 분할 + 프롬프트 강화) 정답 6/12, 거절 8/8, 환각 0. 과잉 거절 A9·A10·A12
- 모델은 바꾸지 않고 프롬프트·검색 결과 전달 방식부터 수정
- 기존에 학습해 둔 1.7B LoRA 어댑터(평가표 4단계)는 과잉 거절은 줄였지만 답이 짧아짐. 파일이 있으면 비교 후보로 사용
- 한 번에 하나만 바꾸고 `scripts/eval_rag.py`로 재측정, `eval/results/`에 저장
- 후보와 순서: [기능별 설계](algorithms.md)의 F-26

</details>
